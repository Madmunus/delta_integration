# Дельта — система управления клиентской базой бухгалтерской фирмы

Прототип веб-системы для агрегации данных о клиентах из «1С» (OData),
управления задачами, контроля сроков отчётности и договоров.

## Возможности

- **ФТ-1** Ролевая модель: руководитель (полный доступ) / сотрудник (только свои клиенты и задачи).
- **ФТ-2** Сводный реестр клиентов: клиенты загружаются из
  `Catalog_Организации` главной базы «1С:Предприятие», контрагенты — из
  `Catalog_Контрагенты`; ручные атрибуты (ответственный, заметки).
- **ФТ-3** Договоры на сопровождение: загрузка из `Catalog_Договоры` по
  индивидуальным реквизитам подключения клиента к «1С:Бухгалтерия»,
  стоимость, сроки действия. У архивных клиентов не может быть проектов
  и действующих договоров — только завершённые.
- **ФТ-4** Отображение входящих документов из «1С:Документооборот» в карточке
  клиента и общем реестре «Документы»: загрузка по всем видам документов
  `Document_*`, вычисление поля «Вид документа» из имени сущности.
- **ФТ-5** Задачи с привязкой к клиентам/сотрудникам, сроками и приоритетами;
  автогенерация задач по справочнику сроков (APScheduler).
- **ФТ-6** Справочник видов отчётности (периодичность, срок сдачи) и визуальный
  контроль ближайших/просроченных сроков в разрезе клиентов.
- **ФТ-7** Сводные отчёты для руководителя: клиенты, задачи, договоры,
  документы, сроки.
- **Аудит записей** — у всех сущностей хранятся дата создания и дата обновления;
  в карточках клиента, контрагента, договора и документа обе даты выводятся
  в формате `дд.мм.гггг чч:мм:сс`, в реестрах столбец называется «Дата создания».

## Технологии

Python 3.10+, Flask, SQLAlchemy, Flask-Login, Flask-WTF (CSRF), Jinja2,
Bootstrap 5 и Font Awesome Free 7.3.1 (хранятся локально в
`static/vendor/`), requests, APScheduler.
СУБД: SQLite (разработка) / PostgreSQL (продакшен).

## Быстрый старт (разработка)

```bash
cd delta_integration
python -m pip install -r requirements.txt
python seed.py                    # демо-данные
python app.py                     # http://127.0.0.1:5000
```

## Продакшен (PostgreSQL)

```bash
set DELTA_ENV=production
set DELTA_SECRET_KEY=<случайная строка>
set DELTA_DATABASE_URL=postgresql+psycopg2://user:pass@host:5432/delta
python -m pip install psycopg2-binary gunicorn
gunicorn -w 4 -b 0.0.0.0:8000 "app:app"
```

> Планировщик (APScheduler) в WSGI-окружении лучше вынести в отдельный процесс
> или cron: `python -m engine.run_jobs`.

## Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DELTA_SECRET_KEY` | ключ сессий (обязателен в проде) | dev |
| `DELTA_DATABASE_URL` | строка подключения | SQLite `delta.db` |
| `DELTA_SYNC_INTERVAL` | период синхронизации клиентов, сек | `3600` |
| `DELTA_DOCUMENTS_INTERVAL` | период загрузки документов, сек | `3600` |
| `DELTA_ODATA_TIMEOUT` | таймаут HTTP-запросов к OData, сек | `15` |
| `DEADLINE_LEAD_DAYS` (DELTA_DEADLINE_LEAD_DAYS) | за сколько дней до срока создавать задачи | `7` |

### Панель управления

Главная страница после входа состоит из блоков по каждому реестру:
«Клиенты», «Контрагенты», «Договоры», «Документы» и «Задачи».
Каждый блок разделён на две части:

- слева — первые 5 записей реестра в порядке сортировки по умолчанию;
  наименования и номера ведут в карточки просмотра;
- справа — сводка: распределение записей по статусам и другим признакам;
  общее количество показано в заголовке блока (у договоров и документов
  дополнительно количество обработанных, у договоров — ещё и сумма
  действующих). Плитки сводки, для которых в реестре есть фильтр,
  кликабельны и открывают реестр с уже выбранным статусом; плитка
  «Обработано» открывает реестр с фильтром «Обработан: Да».

Сотрудник видит в блоках только доступные ему записи: своих клиентов,
их договоры и документы, а также назначенные на него задачи.

### Общие элементы реестров

В реестрах «Клиенты», «Контрагенты», «Договоры», «Документы» и «Задачи»
пагинация по 20 записей вынесена в заголовок страницы и расположена справа.
В реестрах клиентов, контрагентов, договоров, документов и задач фильтр
по дате задаётся одним полем «с — по»; календарь диапазона открывается
при установке фокуса в это поле (отдельной кнопки нет). Значение
поля — `дд.мм.гггг — дд.мм.гггг`; можно ввести одну дату (тогда
отбирается этот день) либо указать только одну границу: «с 15.01.2026»
или «по 31.01.2026». Параметр URL — `date_range`; старые `date_from`
и `date_to` по-прежнему принимаются, а также формат `гггг-мм-дд`.
В реестрах клиентов и контрагентов фильтр работает по дате создания,
в реестрах договоров и документов — по дате документа, в реестре задач —
по сроку выполнения.
В реестре договоров после фильтра по дате идут фильтры по клиенту
и контрагенту — выпадающие списки «Все клиенты» / «Все контрагенты»;
сотруднику в списке клиентов доступны только закреплённые за ним.

Во всех реестрах работает сортировка по столбцам: клик по заголовку
переключает три состояния — по возрастанию ▲ → по убыванию ▼ → сортировка
отключена (по умолчанию). Состояние сортировки передаётся параметрами
`sort` и `dir`, сохраняется при фильтрации и переключении страниц и не
сбрасывает выбранные фильтры. Набор сортируемых столбцов задаётся в
маршруте каждого реестра в словаре `SORTABLE_COLUMNS`, а общий макрос
заголовка находится в `templates/_sort.html`.

### Реестр клиентов

- **Поиск по таблице** — по наименованию, ИНН, КПП и заметкам.
- **Фильтры** — по статусу и диапазону дат создания (единое поле
  «Дата создания: с — по»). Календарь открывается при фокусе на поле;
  диапазон выбирается двумя кликами (начало и конец) либо вводится
  вручную; в запрос передаётся параметр `date_range` в формате
  `дд.мм.гггг — дд.мм.гггг`, при этом параметры URL также принимают
  `дд.мм.гггг` и `гггг-мм-дд`.
  Руководителю доступен ещё и фильтр по ответственному,
  включая вариант «не назначен».
- **Быстрая очистка** — кнопка «×» всегда видна у поля поиска и у поля
  диапазона дат; она очищает только это поле на клиенте, без отправки
  запроса на сервер, и сохраняет остальные фильтры и сортировку.
  Кнопка **«Сброс»** после «Найти» очищает все фильтры сразу.
- **Сортировка** — клик по заголовку столбца (Наименование, ИНН,
  Статус, Ответственный, Дата создания) переключает три состояния:
  по возрастанию ▲ → по убыванию ▼ → сортировка отключена (по умолчанию).
  По умолчанию сначала идут активные клиенты, затем архивные, внутри
  группы — по наименованию. Состояние сортировки сохраняется при
  фильтрации и переключении страниц, а применение сортировки не сбрасывает
  текущую страницу пагинации.
- **Действия** — «Редактировать» открывает карточку клиента; «Удалить»
  (только руководитель) удаляет клиента вместе со всеми связанными
  договорами, задачами и документами (каскадное удаление).
- **Добавление клиентов недоступно**: клиенты поступают только из
  «1С:Предприятие» при синхронизации. В форме редактирования клиента
  доступны только поля «Ответственный сотрудник», «Заметки» и реквизиты
  подключения к «1С:Бухгалтерия». Остальные данные (ID, наименование,
  ИНН, КПП, статус, дата создания, `Ref_Key`) выводятся для информации
  и не редактируются.
- **Добавление договоров недоступно**: договоры загружаются только из
  «1С:Бухгалтерия» клиента при синхронизации.

### Реестр задач

- **Поиск по таблице** — по названию, описанию, клиенту, исполнителю
  и статусу (новая, в работе, выполнена).
- **Фильтры** идут в порядке: «Поиск по таблице», «Клиент», «Исполнитель»
  (доступен руководителю; содержит пункт «Только мои»), диапазон срока
  «Срок: с — по» с календарём, «Приоритет», «Статус» (содержит пункт
  «Просроченные» после «Открытых» — отбор по сроку выполнения, а не по
  статусу).
- **Исполнитель обязателен** — задача не может быть без исполнителя:
  в форме нет варианта «— не назначен —», а создание без исполнителя
  отклоняется с сообщением «Выберите исполнителя задачи». Задачам без
  исполнителя, оставшимся от прежних версий, при запуске назначается
  ответственный клиента (или первый активный пользователь).
- **Сортировка** — по столбцам «Задача», «Клиент», «Исполнитель», «Срок»,
  «Приоритет», «Статус» и «Дата создания». По умолчанию задачи идут
  по статусу: «Новая» → «В работе» → «Выполнена», внутри статуса —
  по приоритету: «Высокий» → «Средний» → «Низкий», внутри приоритета —
  по сроку по возрастанию.
- **Кнопки** — применение фильтра, сброс всех фильтров и синяя кнопка
  с иконкой «+» для создания новой задачи. Руководителю после неё доступна
  красная кнопка с крестиком для удаления всех задач (с подтверждением);
  сотруднику эта кнопка не показывается.
- **Движение по статусам** — в строке задачи две кнопки со стрелками:
  `fa-arrow-left` переводит задачу на предыдущий статус, `fa-arrow-right` —
  на следующий (новая → в работе → выполнена). На краях цепочки
  соответствующая стрелка недоступна.
- **Статус** — выводится цветным бейджем: «новая» — серый, «в работе» —
  синий, «выполнена» — зелёный. Соответствие статусов и CSS-классов задано
  в `Task.STATUS_BADGES`, цвет бейджа возвращает свойство
  `task.status_badge_class`. «Просрочена» статусом не является: если
  срок выполнения прошёл, а задача не выполнена, рядом со статусом
  выводится красный бейдж «просрочена». Признак вычисляется по дате срока
  и не хранится в статусе задачи.
- **Приоритет** — выводится цветным бейджем: «высокий» — красный,
  «средний» — жёлтый, «низкий» — серый. Соответствие задано
  в `Task.PRIORITY_BADGES`, цвет бейджа возвращает свойство
  `task.priority_badge_class`.

Вкладка «Задачи» в карточке клиента оформлена так же, как реестр задач:
те же столбцы (кроме дублирующего «Клиент»), цветные бейджи приоритета
и статуса, отметки срока, ссылка на карточку задачи, стрелки движения
по статусам, кнопки редактирования и удаления.

### Карточки задач

Название задачи в реестре ведёт на страницу просмотра: клиент,
исполнитель, срок (с отметкой «просрочено»/«осталось»), приоритет
(цветным бейджем), статус (с отдельным красным бейджем просрочки по сроку),
описание, даты создания и обновления, признак автогенерации по справочнику
сроков. Из карточки просмотра кнопка «Редактировать» открывает карточку
редактирования; в реестре для этого есть карандаш.

Карточка редактирования задачи оформлена так же, как у остальных
сущностей: заголовок с кнопкой «Просмотр», блок «Данные» только для
чтения (даты и источник автогенерации) и блок «Редактируемые поля»
с формой. Кнопки «Отмена» нет — только сохранение.

### Сроки отчётности

- **Справочник видов отчётности** — код, наименование, периодичность
  (ежемесячная, ежеквартальная, годовая), день сдачи, смещение периода,
  категория налогоплательщика и признак включения. Добавлять и
  редактировать виды отчётности может только руководитель.
- **Окно автогенерации** — задачи создаются за `DEADLINE_LEAD_DAYS` дней
  до срока сдачи (по умолчанию 7). Задача формируется для каждого
  активного клиента по включённым формам его категории; для пары
  «форма + период + клиент» повторно задача не создаётся. Клиенты без
  ответственного пропускаются — иначе задача осталась бы без исполнителя;
  они не учитываются и в предпросмотре.
- **Предпросмотр** — таблица «Контроль ближайших сроков в разрезе
  клиентов» показывает только формы, срок которых попадает в окно
  генерации `[сегодня; сегодня + DEADLINE_LEAD_DAYS]`, то есть именно те,
  по которым кнопка «Сформировать задачи по срокам» создаст задачи.
  В подсказке над таблицей выводится размер окна, дата его окончания
  и ближайший срок за его пределами (с названием формы), если он есть.
  Если сроков в окне нет, вместо строк выводится пояснение
  «Сейчас нет сроков в окне формирования задач (до … включительно)».
- **Сообщение после запуска** — flash показывает число созданных задач.
  Если создано 0, причина указывается явно: задачи по срокам в окне уже
  сформированы, ближайший срок ещё вне окна (с датой и числом дней) или
  в справочнике нет включённых видов отчётности.
- **Расчёт ближайшего срока** — перебором отчётных периодов с запасом
  назад, поэтому квартальные формы со сроком за период нескольких месяцев
  до текущей даты не пропускаются.

### Отчёты

Раздел «Отчёты» доступен только руководителю. В отчёте по клиентской базе:

- плитки «Активных клиентов», «Всего в реестре» и «Без ответственного»
  ведут в реестр клиентов с соответствующим фильтром;
- столбец «Активность» показывает, активен пользователь или отключён
  (бейдж, как в реестре пользователей);
- ФИО в столбце «Ответственный сотрудник» ведёт в карточку пользователя;
- числа в столбцах «Всего клиентов» и «Активных» ведут в реестр клиентов
  с фильтром по ответственному (для активных — ещё и по статусу
  «Активные»);
- строки отсортированы так: сначала активные пользователи, затем
  отключённые; внутри группы — по числу активных клиентов по убыванию,
  при равенстве — по ФИО;
- кнопка со стрелкой в конце строки раскрывает список клиентов
  сотрудника: наименование (ссылка на карточку клиента), ИНН, статус
  и дата добавления.

В отчёте по задачам:

- плитки «Всего задач», «Выполнено», «В работе» и «Просрочено» ведут
  в реестр задач с соответствующим фильтром;
- ФИО исполнителя ведёт в карточку пользователя;
- числа в столбцах «Выполнено», «В работе», «Просрочено» и «Всего» ведут
  в реестр задач с фильтром по исполнителю и статусу;
- задач без исполнителя нет: правило системы — у задачи всегда есть
  исполнитель;
- «Просрочено» — признак срока (задача не выполнена и срок прошёл),
  поэтому такие задачи входят и в «В работе»; «Всего» = «Выполнено» +
  «В работе»;
- столбец «Активность» показывает, активен пользователь или отключён
  (бейдж, как в отчёте по клиентам); строки отключённых выделены серым;
- строки отсортированы так: сначала активные пользователи, затем
  отключённые; внутри группы — по «Просрочено», «В работе» и «Выполнено»
  по убыванию, при равенстве — по ФИО;
- кнопка со стрелкой в конце строки раскрывает список задач исполнителя:
  название (ссылка на карточку задачи), клиент, срок, приоритет и статус.

В отчёте по договорам и поступлениям:

- данные сгруппированы по клиентам: для каждого клиента показаны общее
  число договоров, количество проектов, действующих и завершённых,
  обработанных и необработанных, сумма действующих и сумма всех договоров;
- плитки над таблицей показывают число клиентов с договорами, общее
  число договоров, проекты, действующие, завершённые и обработанные
  договоры; каждая плитка ведёт в реестр с соответствующим фильтром;
- наименование клиента ведёт в карточку клиента, числа — в реестр
  договоров с фильтром по клиенту, статусу и признаку «Обработан»;
- кнопка со стрелкой раскрывает список договоров клиента: номер (ссылка
  на карточку договора), дата, контрагент, стоимость, срок действия
  и статус;
- клиенты отсортированы так: сначала активные по сумме действующих
  договоров по убыванию, при равенстве — по наименованию; архивные
  клиенты идут в конце.

В отчёте по документам:

- данные сгруппированы по клиентам: для каждого клиента показаны общее
  число документов, количество по статусам «Черновик», «Зарегистрирован»,
  «Проведён» и «Отменён», а также обработанные и необработанные;
- плитки над таблицей показывают число клиентов с документами, общее
  число документов, черновики, зарегистрированные, проведённые, отменённые
  и обработанные документы; каждая плитка ведёт в реестр
  с соответствующим фильтром;
- наименование клиента ведёт в карточку клиента, числа — в реестр
  документов с фильтром по клиенту, статусу и признаку «Обработан»;
- кнопка со стрелкой раскрывает список документов клиента: вид документа
  (ссылка на карточку), номер, дата, контрагент, статус и признак
  «Обработан»;
- клиенты отсортированы так: сначала активные по числу документов
  по убыванию, при равенстве — по наименованию; архивные клиенты
  идут в конце.

## Профиль пользователя

Любой пользователь может самостоятельно редактировать свои данные: ссылка
на карточку — это отображаемое ФИО в правом верхнем углу navbar. Сотрудник
может изменить ФИО, логин (email) и пароль; поля «Роль» и «Активен» ему
недоступны и не могут быть изменены через форму. Руководитель в карточке
пользователя дополнительно управляет ролью и активностью.

Список пользователей отсортирован так: сначала руководители, затем
активные пользователи, затем отключённые; внутри каждой группы —
по ФИО по возрастанию.

Пароль вводится дважды — в полях «Пароль» и «Подтверждение пароля»;
значения должны совпадать. При редактировании пустые поля означают
«оставить текущий пароль». Пароль не должен содержать совпадающие части
(от 4 символов) локальной части логина и транслитерации слов ФИО —
например, для `ivanov@delta.local` / «Иванов Пётр» недопустимы `ivan`,
`vano`, `petr` и т. п. (регистр не важен).

## Интеграция с 1С (OData)

### Главная база «1С:Предприятие»

1. Включите публикацию стандартного OData-интерфейса
   (Администрирование → Публикация на веб-сервере → «Стандартный интерфейс OData»).
2. Создайте пользователя 1С с правами на чтение справочников
   `Catalog_Организации` и `Catalog_Контрагенты`.
3. В системе откройте раздел **«1С База»** и заполните единственную настройку:
   URL OData, пользователь, пароль. Нажмите «Сохранить настройку».
4. Кнопка «Синхронизировать клиентов и контрагентов» загружает:
   - клиентов из `Catalog_Организации` (`Ref_Key`, `Наименование`, `ИНН`,
     `DeletionMark`: `0` — активный, `1` — архивный);
   - контрагентов из `Catalog_Контрагенты` (`Ref_Key`,
     `НаименованиеПолное`, `ИНН`, `КПП`, `DeletionMark`;
     `DeletionMark`: `0` — «активный», `1` — «архивный»;
   Загруженные контрагенты отображаются в отдельном разделе «Контрагенты».
   В реестре есть поиск по таблице (наименование, ИНН, КПП, заметки), фильтры
   по активности записи (активные / архивные) и по дате создания, сортировка
   по столбцам «Наименование», «ИНН», «Статус», «Заметки» и «Дата создания»,
   столбец «Статус» и столбец с
   кнопкой-карандашом для перехода в карточку редактирования; столбец КПП
   скрыт, но поиск по нему сохранён.
   Из списка открывается карточка контрагента с вкладками «Данные»,
   «Договоры» и «Документы». Таблицы этих вкладок оформлены так же, как
   соответствующие реестры: те же столбцы (кроме дублирующего контрагента),
   статусы-бейджи и кнопки редактирования; в документах вид документа ведёт
   в карточку, а ссылка на объект 1С вынесена в кнопку «1С».
   Сотрудник видит в карточке только договоры
   и документы по закреплённым за ним клиентам; руководитель — по всем.
   В карточке редактирования контрагента меняются только «Заметки»,
   остальные данные выводятся для информации и не редактируются.
   Блок «Состояние синхронизации» показывает дату создания настройки,
   время последней синхронизации и счётчики: клиентов в реестре (ссылка
   на страницу «Клиенты»), клиентов с подключением к «1С:Бухгалтерия»,
   контрагентов и документов (ссылки на соответствующие реестры).
5. Синхронизация также выполняется автоматически (по умолчанию раз в час).
   Документы из «1С:Документооборот» загружаются автоматически с тем же
   периодом (настраивается `DELTA_DOCUMENTS_INTERVAL`).

Сопоставление клиентов и контрагентов: по `Ref_Key` (GUID объекта 1С),
затем по ИНН. Ручные атрибуты клиентов (ответственный, заметки, реквизиты
подключения к «1С:Бухгалтерия») при синхронизации не перезаписываются.

### Договоры клиента из «1С:Бухгалтерия»

Каждый клиент может иметь собственные URL OData, пользователя и пароль
для доступа к своей базе «1С:Бухгалтерия» (поля в карточке клиента).
По этим реквизитам загружается справочник `Catalog_Договоры`:
`Ref_Key`, `Контрагент`, `Наименование`, `Дата`, `СрокДействия`,
`Статус`, `Сумма`, `Description`.

Загрузка запускается кнопкой «Загрузить договоры из 1С» в карточке клиента
или общей кнопкой «Синхронизировать договоры» на странице «1С База».
Договор привязывается к контрагенту по `Контрагент`; статус из 1С
приводится к внутренним значениям (`active`, `closed`, `draft`), исходное
значение сохраняется отдельно. Статус выводится цветным бейджем:
«действующий» — зелёный, «завершённый» — серый, «проект» — светлый;
соответствие задано в `Contract.STATUS_BADGES`, цвет возвращает свойство
`contract.status_badge_class`. В реестре договоров есть поиск по таблице,
фильтры по статусу, признаку «Обработан» и дате договора, сортировка по
столбцам «Номер», «Дата», «Клиент», «Контрагент», «Стоимость»,
«Срок действия», «Статус», «Обработан» и «Дата создания», пагинация
по 20 записей. Признак «Обработан» выводится в таблице бейджем «Да»/«Нет»,
а фильтр принимает значения `processed=yes` и `processed=no`.
Без выбранной сортировки договоры
идут по статусу: «Проект» → «Действует» → «Закрыт», внутри статуса — по дате
по убыванию, затем по номеру по возрастанию.
В карточке редактирования договора меняются признак «Обработан» и «Заметки»
(внутреннее поле пользователя, синхронизацией не перезаписывается);
остальные реквизиты выводятся только для чтения.

У архивных клиентов не может быть проектов и действующих договоров.
При синхронизации клиентов (`DeletionMark = 1`) все открытые договоры
автоматически переводятся в «завершённые», а договоры, загружаемые из
«1С:Бухгалтерия» для архивного клиента, сохраняются как завершённые
(исходный статус 1С остаётся в поле `status_1c`). Правило применяется
также к уже существующим данным при запуске приложения и при выполнении
`seed.py`; в карточке архивного клиента выводится соответствующее
предупреждение.

### Документы из «1С:Документооборот»

Загружаются все виды документов из перечня `DOCUMENT_ENTITIES`
(`Document_РеализацияТоваровУслуг`, `Document_СчетНаОплатуПокупателю`,
`Document_ПоступлениеНаРасчетныйСчет`, `Document_ПлатежноеПоручение`
и другие — всего 28 видов). По каждому документу 1С возвращает поля
`Ref_Key`, `Организация`, `Контрагент` (может быть пустым), `Номер`
(`Number`), `Дата` (`Date`) и `Статус`.

Поле **«Вид документа»** вычисляется автоматически: это имя сущности
без префикса `Document_` (например,
`Document_РеализацияТоваровУслуг` → `РеализацияТоваровУслуг`).
Документ привязывается к клиенту по `Организация`; если контрагент
не указан, документ сохраняется без контрагента. Документы с неизвестной
организацией пропускаются, повторная загрузка не создаёт дублей.
По умолчанию из 1С запрашиваются документы за последние 30 дней; этот
период передаётся в OData-фильтр `Date`, поэтому больше данных не выгружается.

Поле **«Ссылка»** заполняется при загрузке: используется явное поле
ответа 1С (`Ссылка`/`URL`), канонический адрес `__metadata.uri` либо
deep link веб-клиента `.../e1cib/data/Документ.<Вид>?ref=<GUID>`.
В реестре и карточках ссылка открывает объект в «1С:Документооборот»:
в таблицах это кнопка «1С» в столбце действий.

Загрузку можно запустить кнопкой «Синхронизировать документы» на странице
**«1С База»**, из карточки клиента (кнопка «Загрузить договоры из 1С»
загружает договоры, а документы — по расписанию/кнопке) или вручную
командой `python -m engine.run_jobs` (однократный запуск всех заданий).

Все загруженные документы доступны в общем реестре **«Документы»**:
вид документа, номер, дата, клиент, контрагент и статус. Статус выводится
цветным бейджем: «Черновик» — серый, «На согласовании» — жёлтый,
«Зарегистрирован» — синий, «Проведён» — зелёный, «Отменён» — красный;
для остальных статусов используется нейтральный тёмный бейдж.
Соответствие задано в `Document.STATUS_BADGES`; при поиске цвета статус
нормализуется (нижний регистр, «ё» → «е»), цвет возвращает свойство
`document.status_badge_class`.
В реестре есть поиск по таблице, фильтры по статусу, клиенту, признаку
«Обработан» и дате документа, сортировка по столбцам «Вид документа», «Номер», «Дата»,
«Клиент», «Контрагент», «Статус», «Обработан» и «Дата создания», пагинация
по 20 записей; признак «Обработан» выводится бейджем «Да»/«Нет», а фильтр
принимает значения `processed=yes` и `processed=no`; сотрудник
видит документы только клиентов, закреплённых за ним. Без выбранной сортировки документы
идут по статусу: «Черновик» → «Зарегистрирован» → «Проведён» → «Отменён»,
внутри статуса — по дате по убыванию, затем по номеру по возрастанию. Ссылка на карточку находится
в столбце «Вид документа».
В последнем столбце — кнопки действий: синяя «1С» (если заполнена ссылка
на объект в «1С:Документооборот») и карандаш для перехода в карточку
редактирования документа.
Из реестра открывается карточка документа с данными, ссылкой
и датами создания и обновления. В карточке редактирования документа
меняются признак «Обработан» и «Заметки» — внутренние поля пользователя,
которые синхронизация из 1С не читает и не перезаписывает.

## Тестирование системы

Страница **«Тестирование»** (меню руководителя, после «Пользователи»)
выполняет восемь сценариев проверки функциональных требований:

| Сценарий | ФТ | Проверка |
|---|---|---|
| 1 | ФТ-1 | вход под сотрудником; видимость только закреплённых клиентов |
| 2 | ФТ-2 | синхронизация клиентов (`Catalog_Организации`) и контрагентов (`Catalog_Контрагенты`); учёт `DeletionMark`; отсутствие дублей |
| 3 | ФТ-3 | загрузка договоров из `Catalog_Договоры` по реквизитам клиента; привязка к контрагенту, статусы, отсутствие дублей; у архивного клиента только завершённые договоры |
| 4 | ФТ-4 | загрузка документов по видам `Document_*`; вычисление «Вида документа»; пустой контрагент; отображение в карточке клиента; карточка документа с датами |
| 5 | ФТ-5 | создание задачи с привязкой к клиенту и исполнителю; смена статусов; сводка задач на панели управления |
| 6 | ФТ-6 | формирование задач по справочнику сроков; корректность сроков; архивы не обрабатываются; предпросмотр ближайших сроков; отсутствие отдельной страницы «Контроль сроков сдачи отчётности» |
| 7 | ФТ-7 | отчёты по клиентской базе, задачам и договорам (в разрезе клиентов); корректность агрегированных показателей |
| 8 | Интерфейс | AJAX-запуск сценариев, пошаговый вывод каждого шага, обычный POST без JavaScript, запрет для сотрудника |

Страница работает через AJAX: запуск сценария — `POST /testing/run/<id>`
с JSON-сводкой, а результат каждого шага — отдельный запрос
`GET /testing/run/<id>/step?index=N`, поэтому таблица заполняется по одному
шагу. Кнопка «Выполнить все» в живом приложении запускает сценарии в фоне
и опрашивает состояние задания; в тестовом режиме запуск остаётся
синхронным. Без JavaScript формы отправляются обычным POST с редиректом.

Каждый сценарий выполняется в изолированном приложении с собственной
базой SQLite в памяти: рабочие данные не затрагиваются, обращения к «1С»
имитируются подставными ответами OData. Тот же набор сценариев доступен
из командной строки:

```bash
python -m tests.runner
```

Команда возвращает код выхода 0 (все пройдены) или 1 (есть непройденные).

## Безопасность

- Пароли хранятся в виде хешей (`generate_password_hash`, Werkzeug/PBKDF2).
- Политика паролей: не менее 13 символов, минимум одна цифра,
  заглавная и строчная латинские буквы, спецсимвол; пароль не должен
  содержать частей логина и транслитерации ФИО. Пароль вводится дважды
  и проверяется на совпадение.
- Все формы защищены CSRF-токенами (Flask-WTF).
- SQLAlchemy ORM исключает SQL-инъекции; Jinja2 автоматически экранирует вывод.
- Проверка прав в каждом обработчике: сотрудник видит только «своих» клиентов и задачи.
- Удаление клиентов и доступ к отчётам/тестированию/пользователям — только для руководителя.
- Каждый пользователь может редактировать только свои данные; чужую
  карточку открыть нельзя (403), роли и активность меняет только руководитель.
- HTTP-запросы к 1С выполняются с таймаутами и обработкой ошибок.
