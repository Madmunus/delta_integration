# Дельта — система управления клиентской базой бухгалтерской фирмы

Прототип веб-системы для агрегации данных о клиентах из «1С» (OData),
управления задачами, контроля сроков отчётности и договоров.

## Возможности

- **ФТ-1** Сводный реестр клиентов: клиенты загружаются из
  `Catalog_Организации` главной базы «1С:Предприятие», контрагенты — из
  `Catalog_Контрагенты`; ручные атрибуты (ответственный, заметки).
- **ФТ-2** Отображение входящих документов из «1С:Документооборот» в карточке
  клиента: загрузка по всем видам документов `Document_*`, вычисление поля
  «Вид документа» из имени сущности.
- **ФТ-3** Задачи с привязкой к клиентам/сотрудникам, сроками и приоритетами;
  автогенерация задач по справочнику сроков (APScheduler).
- **ФТ-4** Справочник видов отчётности (периодичность, срок сдачи) и визуальный
  контроль ближайших/просроченных сроков в разрезе клиентов.
- **ФТ-5** Договоры на сопровождение: загрузка из `Catalog_Договоры` по
  индивидуальным реквизитам подключения клиента к «1С:Бухгалтерия»,
  стоимость, сроки действия.
- **ФТ-6** Сводные отчёты для руководителя: клиенты, задачи, договоры, сроки.
- **ФТ-7** Ролевая модель: руководитель (полный доступ) / сотрудник (только свои клиенты и задачи).

## Технологии

Python 3.10+, Flask, SQLAlchemy, Flask-Login, Flask-WTF (CSRF), Jinja2,
Bootstrap 5 и Font Awesome Free 7.3.1 (хранятся локально в
`static/vendor/`), requests, APScheduler.
СУБД: SQLite (разработка) / PostgreSQL (продакшен).

## Быстрый старт (разработка)

```bash
cd delta_integration
python -m pip install -r requirements.txt
python seed.py                    # демо-данные
python app.py                     # http://127.0.0.1:5000
```

## Продакшен (PostgreSQL)

```bash
set DELTA_ENV=production
set DELTA_SECRET_KEY=<случайная строка>
set DELTA_DATABASE_URL=postgresql+psycopg2://user:pass@host:5432/delta
python -m pip install psycopg2-binary gunicorn
gunicorn -w 4 -b 0.0.0.0:8000 "app:app"
```

> Планировщик (APScheduler) в WSGI-окружении лучше вынести в отдельный процесс
> или cron: `python -m services.run_jobs`.

### Реестр клиентов

- **Поиск по таблице** — по наименованию, ИНН, КПП и заметкам.
- **Фильтры** — по статусу и диапазону дат добавления («с» / «по»).
  Поля дат — стандартные поля выбора даты с календарём; в запрос
  передаётся формат `гггг-мм-дд`, при этом параметры URL также принимают
  `дд.мм.гггг`. Руководителю доступен ещё и фильтр по ответственному,
  включая вариант «не назначен».
- **Быстрая очистка** — кнопка «×» всегда видна у поля поиска и у каждой
  даты; она очищает только это поле на клиенте, без отправки запроса
  на сервер, и сохраняет остальные фильтры и сортировку.
  Кнопка **«Сброс»** после «Найти» очищает все фильтры сразу.
- **Сортировка** — клик по заголовку столбца (Наименование, ИНН, КПП,
  Статус, Ответственный, Добавлен) переключает три состояния:
  по возрастанию ▲ → по убыванию ▼ → сортировка отключена (по умолчанию).
  По умолчанию сначала идут активные клиенты, затем архивные, внутри
  группы — по наименованию. Состояние сортировки сохраняется при
  фильтрации и переключении страниц.
- **Действия** — «Редактировать» открывает карточку клиента; «Удалить»
  (только руководитель) удаляет клиента вместе со всеми связанными
  договорами, задачами и документами (каскадное удаление).
- **Добавление клиентов недоступно**: клиенты поступают только из
  «1С:Предприятие» при синхронизации. В форме редактирования клиента
  доступны только поля «Ответственный сотрудник», «Заметки» и реквизиты
  подключения к «1С:Бухгалтерия». Остальные данные (ID, наименование,
  ИНН, КПП, статус, дата добавления, `Ref_Key`) выводятся для информации
  и не редактируются.
- **Добавление договоров недоступно**: договоры загружаются только из
  «1С:Бухгалтерия» клиента при синхронизации.

## Профиль пользователя

Любой пользователь может самостоятельно редактировать свои данные: ссылка
на карточку — это отображаемое ФИО в правом верхнем углу navbar. Сотрудник
может изменить ФИО, логин (email) и пароль; поля «Роль» и «Активен» ему
недоступны и не могут быть изменены через форму. Руководитель в карточке
пользователя дополнительно управляет ролью и активностью.

Пароль вводится дважды — в полях «Пароль» и «Подтверждение пароля»;
значения должны совпадать. При редактировании пустые поля означают
«оставить текущий пароль». Пароль не должен содержать совпадающие части
(от 4 символов) локальной части логина и транслитерации слов ФИО —
например, для `ivanov@delta.local` / «Иванов Пётр» недопустимы `ivan`,
`vano`, `petr` и т. п. (регистр не важен).

## Интеграция с 1С (OData)

### Главная база «1С:Предприятие»

1. Включите публикацию стандартного OData-интерфейса
   (Администрирование → Публикация на веб-сервере → «Стандартный интерфейс OData»).
2. Создайте пользователя 1С с правами на чтение справочников
   `Catalog_Организации` и `Catalog_Контрагенты`.
3. В системе откройте раздел **«1С База»** и заполните единственную настройку:
   URL OData, пользователь, пароль. Нажмите «Сохранить настройку».
4. Кнопка «Синхронизировать клиентов и контрагентов» загружает:
   - клиентов из `Catalog_Организации` (`Ref_Key`, `Наименование`, `ИНН`,
     `DeletionMark`; `0` — активный, `1` — архивный);
   - контрагентов из `Catalog_Контрагенты` (`Ref_Key`,
     `НаименованиеПолное`, `ИНН`, `КПП`, `Description`).
   Загруженные контрагенты отображаются в отдельном разделе «Контрагенты».
   В реестре есть поиск по таблице (наименование, ИНН, КПП, описание).
   Из списка открывается карточка контрагента с вкладками «Реквизиты»,
   «Договоры» и «Документы». Сотрудник видит в карточке только договоры
   и документы по закреплённым за ним клиентам; руководитель — по всем.
5. Синхронизация также выполняется автоматически (по умолчанию раз в час).

Сопоставление клиентов и контрагентов: по `Ref_Key` (GUID объекта 1С),
затем по ИНН. Ручные атрибуты клиентов (ответственный, заметки, реквизиты
подключения к «1С:Бухгалтерия») при синхронизации не перезаписываются.

### Договоры клиента из «1С:Бухгалтерия»

Каждый клиент может иметь собственные URL OData, пользователя и пароль
для доступа к своей базе «1С:Бухгалтерия» (поля в карточке клиента).
По этим реквизитам загружается справочник `Catalog_Договоры`:
`Ref_Key`, `Контрагент`, `Наименование`, `Дата`, `СрокДействия`,
`Статус`, `Сумма`, `Description`.

Загрузка запускается кнопкой «Загрузить договоры из 1С» в карточке клиента
или общей кнопкой «Синхронизировать договоры» на странице «1С База».
Договор привязывается к контрагенту по `Контрагент`; статус из 1С
приводится к внутренним значениям (`active`, `closed`, `draft`), исходное
значение сохраняется отдельно.

### Документы из «1С:Документооборот»

Загружаются все виды документов из перечня `DOCUMENT_ENTITIES`
(`Document_РеализацияТоваровУслуг`, `Document_СчетНаОплатуПокупателю`,
`Document_ПоступлениеНаРасчетныйСчет`, `Document_ПлатежноеПоручение`
и другие — всего 28 видов). По каждому документу 1С возвращает поля
`Ref_Key`, `Организация`, `Контрагент` (может быть пустым), `Номер`
(`Number`), `Дата` (`Date`) и `Статус`.

Поле **«Вид документа»** вычисляется автоматически: это имя сущности
без префикса `Document_` (например,
`Document_РеализацияТоваровУслуг` → `РеализацияТоваровУслуг`).
Документ привязывается к клиенту по `Организация`; если контрагент
не указан, документ сохраняется без контрагента. Документы с неизвестной
организацией пропускаются, повторная загрузка не создаёт дублей.

## Тестирование системы

Страница **«Тестирование»** (меню руководителя, после «Пользователи»)
выполняет семь сценариев проверки функциональных требований:

| Сценарий | ФТ | Проверка |
|---|---|---|
| 1 | ФТ-1 | синхронизация клиентов (`Catalog_Организации`) и контрагентов (`Catalog_Контрагенты`); учёт `DeletionMark`; отсутствие дублей |
| 2 | ФТ-2 | загрузка документов по видам `Document_*`; вычисление «Вида документа»; пустой контрагент; отображение в карточке клиента |
| 3 | ФТ-3 | создание задачи с привязкой к клиенту и исполнителю; смена статусов; виджет «Мои задачи» |
| 4 | ФТ-4 | формирование задач по справочнику сроков; корректность сроков; архивы не обрабатываются |
| 5 | ФТ-5 | загрузка договоров из `Catalog_Договоры` по реквизитам клиента; привязка к контрагенту, статусы, отсутствие дублей |
| 6 | ФТ-6 | отчёты по клиентской базе и задачам; корректность агрегированных показателей |
| 7 | ФТ-7 | вход под сотрудником; видимость только закреплённых клиентов |

Каждый сценарий выполняется в изолированном приложении с собственной
базой SQLite в памяти: рабочие данные не затрагиваются, обращения к «1С»
имитируются подставными ответами OData. Тот же набор сценариев доступен
из командной строки:

```bash
python -m tests.runner
```

Команда возвращает код выхода 0 (все пройдены) или 1 (есть непройденные).

## Безопасность

- Пароли хранятся в виде хешей (`generate_password_hash`, Werkzeug/PBKDF2).
- Политика паролей: не менее 13 символов, минимум одна цифра,
  заглавная и строчная латинские буквы, спецсимвол; пароль не должен
  содержать частей логина и транслитерации ФИО. Пароль вводится дважды
  и проверяется на совпадение.
- Все формы защищены CSRF-токенами (Flask-WTF).
- SQLAlchemy ORM исключает SQL-инъекции; Jinja2 автоматически экранирует вывод.
- Проверка прав в каждом обработчике: сотрудник видит только «своих» клиентов и задачи.
- Удаление клиентов и доступ к отчётам/тестированию/пользователям — только для руководителя.
- Каждый пользователь может редактировать только свои данные; чужую
  карточку открыть нельзя (403), роли и активность меняет только руководитель.
- HTTP-запросы к 1С выполняются с таймаутами и обработкой ошибок.
